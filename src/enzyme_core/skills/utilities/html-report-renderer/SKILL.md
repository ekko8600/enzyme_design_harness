# HTML Report Renderer

Use this skill for every project step that creates a user-facing `.html` file.
It packages the core practical lessons from `Leonxlnx/taste-skill` for this
scientific reporting context: read the audience, avoid generic AI-looking
defaults, preserve function, and ship complete, readable output.

## Rendering Contract

1. First identify the report type: evidence audit, candidate QC, model results,
   final design summary, or workflow state.
2. Keep the report dense enough for engineering review, but not visually flat:
   strong title, short subtitle, clear sections, metrics, tables, status chips,
   and contextual callouts.
3. Use one restrained accent palette. Avoid purple/blue AI gradients,
   glass-heavy decoration, oversized marketing heroes, and card spam.
4. Prefer semantic HTML: `main`, `header`, `section`, `article`, `table`,
   `details`, `summary`, `footer`.
5. Escape all dynamic text. Only preserve trusted prebuilt HTML fragments.
6. Tables must be readable on mobile using horizontal overflow.
7. Human-readable Markdown reports should get an HTML companion when possible.
8. The generated document should include
   `<meta name="generator" content="opencode-html-report-renderer">`.

## Helper Command

Polish an existing HTML file:

```bash
enzyme-core run html-report-renderer --work-dir ./runs/html-report-renderer --operation render_html -- \
  --input raw_report.html \
  --output polished_report.html \
  --title "Proteinase K candidate QC"
```

Render an inline body fragment:

```bash
enzyme-core run html-report-renderer --work-dir ./runs/html-report-renderer --operation render_html -- \
  --body '<section><h2>Summary</h2><p>Ready for review.</p></section>' \
  --output report.html \
  --title "Design summary"
```

## Design Rules For Enzyme Reports

- Use report-scale typography, not landing-page hero typography.
- Use a quiet light surface by default; dark mode is allowed only when the
  surrounding artifact already depends on it.
- Use status colors only for status: green for complete, amber for review,
  red for blocked or failed.
- For numeric scores, use tabular numbers and keep the raw value visible.
- Preserve provenance links and artifact paths in `code` or table cells.
- Do not hide weak evidence behind visual polish. Flag missing or low-confidence
  data with visible callouts.
- Keep CTAs out of scientific reports unless they are real workflow commands.

## Taste-Skill Adaptation

The source project is built for broad frontend taste. In this project, its core
ideas are narrowed to report rendering:

- infer the audience and document type before choosing density;
- remove generic visual cliches;
- improve typography, spacing, color consistency, hover/focus states, and
  mobile behavior;
- preserve existing stack and functionality instead of rewriting from scratch;
- produce complete output with no placeholder sections.
